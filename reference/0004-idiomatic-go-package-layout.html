Reference: Idiomatic Go Package Layout & Project Architecture

Authoritative guide on package naming, circular dependency avoidance, and project organization in production Go.

The Golden Rules of Go Package Design:
  1. Name by what it provides, not what it contains: Package names are lowercase singular nouns (sqlite, order, http), never generic drawers (models, stores, utils, common).
  2. Eliminate Stutter: The caller sees package.Symbol. Never repeat the package name in the type (sqlite.OrderStore, NOT store.OrderSQLStore; ring.New(), NOT ring.NewRing()).
  3. Respect the Dependency Arrow: Go strictly forbids cyclic imports. Dependencies must form a Directed Acyclic Graph (DAG).

1. Architectural Pattern Comparison

Pattern Structure Pros & Cons in Go
1. Package by Layer (Anti-Pattern) internal/models/
internal/stores/
internal/handlers/		 ❌ Severe stuttering (models.OrderModel, stores.OrderStore)
❌ Almost inevitable cyclic imports as models and stores reference each other
❌ Low cohesion (1 feature spread over 5 directories)
2. Ben Johnson's Standard Package Layout internal/domain/ (pure types & interfaces)
internal/sqlite/ (db implementation)
internal/http/ (web endpoints)
cmd/server/main.go (wiring) 		✅ Zero circular imports: domain depends on nothing
✅ Zero stutter: sqlite.NewOrderStore(db) returns domain.OrderStore
✅ Swappable infrastructure (e.g. SQLite to Postgres, or memory mocks)
3. Package by Feature (Vertical Slices) internal/order/ (model, store, handler)
internal/inventory/ (model, store, handler)
internal/billing/ 		✅ High cohesion for standalone domains
✅ Clean naming: order.NewStore(), order.NewHandler()
⚠️ Watch out for cross-domain cycles: If order imports inventory and inventory imports order, compilation fails!

2. The Stutter Test: Caller-Site Ergonomics

Always evaluate your naming from the perspective of the caller:

// ❌ Bad (Stutter & Generic Layer):
import "github.com/my/app/internal/stores"
s := stores.NewOrderSQLStore(db) // Reads as: stores.NewOrderSQLStore

// ✅ Good (Driver-based Package):
import "github.com/my/app/internal/sqlite"
s := sqlite.NewOrderStore(db) // Reads as: sqlite.NewOrderStore

// ✅ Good (Feature-based Package):
import "github.com/my/app/internal/order"
s := order.NewSQLiteStore(db) // Reads as: order.NewSQLiteStore

3. Preventing Cyclic Imports in Feature Packages

If you choose Package-by-Feature (e.g. internal/order and internal/inventory), how do they communicate without cycles?

  1. Pass Primitive IDs: Instead of order.Item depending on inventory.Stock, pass scalar IDs: itemID uuid.UUID or string identifiers.
  2. Define Interfaces at the Consumer: package order defines: 
    type StockChecker interface {
    HasStock(ctx context.Context, itemID uuid.UUID, qty int) bool
}
    order does NOT import inventory! An adapter or orchestrator in cmd/ wires them together.
  3. High-Level Orchestrator: A workflow/processor package (like internal/processor) imports both order and inventory and coordinates them in a pipeline.
