Lesson 0048: OpenTelemetry Distributed Tracing & Span Lifecycle

Target: Master production observability. Trace requests from HTTP/Connect-RPC handlers through the transactional outbox and worker goroutines into SQLite transactions using OpenTelemetry.

Why Your Dashboard Panicked (The ServeMux Precedence Trap):

You saw this panic when restoring the file server:

panic: pattern "GET /" conflicts with pattern "/order.v1.OrderService/":
GET / matches fewer methods than /order.v1.OrderService/, but has a more general path pattern

In Go 1.22+, http.ServeMux forbids ambiguous pattern overlaps:

  • "/order.v1.OrderService/" specifies no method (matches ANY method: GET, POST, OPTIONS, etc.).
  • "GET /" specifies method GET, but its path (/) is more general than /order.v1.OrderService/!
  • If a GET /order.v1.OrderService/foo arrives, neither pattern is strictly more specific! One is more specific on method, the other is more specific on path.

The Fix: Register mux.Handle("/", web.FileServer()) without the "GET " prefix. Now both match all methods, and /order.v1.OrderService/ is longer than /, so ServeMux has zero ambiguity!

1. What Is OpenTelemetry (OTel)?

In production distributed architectures, an order lifecycle touches multiple asynchronous boundaries:

  1. An HTTP or Connect-RPC request hits the server (Root Span).
  2. A SQLite transaction saves the order with status PENDING (Child Span: db.SaveOrder).
  3. An asynchronous Outbox dispatcher polls and claims the order (Span: outbox.Claim).
  4. A worker pool picks up the order and executes parallel sagas (Span: processor.OrderPlacing & Span: processor.Paying).

Without distributed tracing, diagnosing why an order took 2.5 seconds requires sifting through thousands of log lines across different goroutines. With OpenTelemetry, every step is linked under a single Trace ID with exact latency breakdowns!

2. The OpenTelemetry Tracer Blueprint

// internal/telemetry/tracer.go
package telemetry

import (
    "context"
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/trace"
    "go.opentelemetry.io/otel/trace/noop"
)

var Tracer = otel.Tracer("gopher-order")

// StartSpan creates a child span linked to the incoming context
func StartSpan(ctx context.Context, name string, opts ...trace.SpanStartOption) (context.Context, trace.Span) {
    return Tracer.Start(ctx, name, opts...)
}

3. Tracing Inside Your Processors

func (p *OrderPlacing[T]) Process(ctx context.Context, order *domain.Order) (func(context.Context) error, error) {
    ctx, span := telemetry.StartSpan(ctx, "processor.OrderPlacing")
    defer span.End()

    // Pass the traced context directly to database operations!
    tx, err := p.db.BeginTx(ctx, nil)
    ...
}

Your Hands-On Challenge

  1. Install the core OpenTelemetry packages: 
    go get go.opentelemetry.io/otel go.opentelemetry.io/otel/trace
  2. Create internal/telemetry/tracer.go:
    • Define a package-level tracer named "gopher-order".
    • Export a helper function StartSpan(ctx context.Context, name string) (context.Context, trace.Span).
  3. Instrument internal/processor/order_placing.go:
    • Start a span named "processor.OrderPlacing" at the beginning of Process.
    • Ensure defer span.End() is called.
  4. Instrument internal/http/order_rpc.go:
    • Start a span named "rpc.CreateOrder" and "rpc.GetOrder".
  5. Run your test suite to ensure 100% pass rate with zero overhead: 
    go test -v -race ./...
