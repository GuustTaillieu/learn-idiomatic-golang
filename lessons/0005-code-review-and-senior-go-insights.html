2. Senior Refinement #1: Pointer vs Value Semantics

In task.go, you wrote:

func NewTask(payload string) *Task { ... }

And in your test, notice what you had to do:

q.Submit(ctx, *NewTask(...)) // Notice the asterisk!

Why did you have to dereference it with *? Because NewTask returns a pointer (*Task), but Submit(ctx, task Task) expects a value (Task).

Senior Guideline: In Go, pick a semantic for each type and stick to it:

  • If Task is an immutable value object, have NewTask(...) Task return by value.
  • If Task represents a stateful entity whose status changes (StatusRunning, StatusCompleted), pass *Task everywhere (chan *Task, Submit(ctx, t *Task)).

3. Senior Refinement #2: "Make the Zero Value Useful"

One of Go's famous proverbs is: "Make the zero value useful."

In queue.go, you wrote:

return &Queue{
    processor: processor,
    tasks:     make(chan Task, 100),
    wg:        sync.WaitGroup{}, // Unnecessary
    mu:        sync.RWMutex{},   // Unnecessary
    closed:    false,            // Unnecessary
}

In Go, newly allocated memory is automatically zeroed out. The zero value of a sync.Mutex is already an unlocked, valid mutex. The zero value of a sync.WaitGroup is an active counter of 0. The zero value of bool is false.

So idiomatic Go simply omits them:

return &Queue{
    processor: processor,
    tasks:     make(chan Task, 100),
}

4. Senior Refinement #3: The Hidden Lock Contention Edge Case

Look at your Submit method:

func (q *Queue) Submit(ctx context.Context, task Task) error {
    q.mu.RLock()
    defer q.mu.RUnlock()

    if q.closed {
        return ErrQueueClosed
    }

    select {
    case q.tasks <- task:
        return nil
    case <-ctx.Done():
        return fmt.Errorf("task submission failed: %w", ctx.Err())
    }
}

What happens if the buffer (100 tasks) is completely full? q.tasks <- task will pause and wait. But while it is waiting, it is still holding q.mu.RLock()!

If someone calls q.Stop() right now, q.Stop() tries to call q.mu.Lock() (exclusive lock). It will be blocked waiting for Submit to release its read lock! But Submit won't release its lock until a worker pulls a task!

This is called Lock Contention. In modern Go, we solve this by introducing a stopCh chan struct{} so Submit can exit immediately without holding a lock during the channel send.
