Lesson 0002: Goroutines, Worker Pools, and sync.WaitGroup

Target: Learn how background workers consume from channels and how to track their lifecycle.

Win: You just implemented Submit() with a read-lock and context select! Now we build the consumer side: the worker pool that pulls tasks off the channel and processes them.

1. Mental Model: What is a Worker in Go?

In Go, we don't have heavy thread pools managed by the OS. Goroutines are lightweight (starting at only ~2KB of memory), scheduled cooperatively by the Go runtime (the M:N scheduler).

A "worker" is simply a long-running goroutine executing a loop that waits for work on a channel:

func (q *Queue) worker(ctx context.Context) {
    defer q.wg.Done()

    for {
        select {
        case <-ctx.Done():
            return // Shutdown requested!
        case task, ok := <-q.tasks:
            if !ok {
                return // The channel was closed!
            }
            // Execute the work!
            _ = q.processor.Process(ctx, task.Payload)
        }
    }
}

2. The "Comma-OK" Idiom on Channels

Notice task, ok := <-q.tasks. Why not just task := <-q.tasks?

In Go, when a channel is closed, receiving from it does not block or crash. Instead, it immediately produces the type's zero-value (an empty Task{})!

To differentiate between an empty task that was genuinely sent versus a closed channel, Go gives us the boolean ok:

  • ok == true: A real task was sent and received.
  • ok == false: The channel is closed and drained! We should exit the worker loop.

3. The sync.WaitGroup Triangle

You already added wg sync.WaitGroup to the Queue struct. Here is how it works:

  1. wg.Add(1): Increment the counter. Critical Senior Rule: Always call Add() in the spawning goroutine before launching the go worker(), never inside the worker itself (to avoid a race where Wait() checks before Add() runs).
  2. defer wg.Done(): Inside the worker, decrement the counter when the worker function exits.
  3. wg.Wait(): Used during shutdown to block until every single worker has finished and the counter reaches 0.

4. Spawning the Pool: Start()

A senior Go queue controls its concurrency limit through a numWorkers parameter:

func (q *Queue) Start(ctx context.Context, numWorkers int)

This spins up N worker goroutines, each running concurrently and sharing the single q.tasks channel. Go automatically balances the incoming tasks across whoever is ready!

Your Hands-On Challenge: Implement worker and Start

In internal/queue/queue.go:

  1. Add an unexported method func (q *Queue) worker(ctx context.Context):
    • Call defer q.wg.Done() right at the start.
    • Write a for { select { ... } } loop handling both <-ctx.Done() and task, ok := <-q.tasks.
    • If a task is received and ok is true, invoke q.processor.Process(ctx, task.Payload).
  2. Add a public method func (q *Queue) Start(ctx context.Context, numWorkers int):
    • Loop from 0 to numWorkers.
    • For each iteration, call q.wg.Add(1) and launch the worker in a goroutine: go q.worker(ctx).
