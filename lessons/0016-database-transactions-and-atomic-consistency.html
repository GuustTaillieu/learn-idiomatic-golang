1. Why Mutexes Cannot Prevent "Half-Done" Business Work

You asked an insightful question:

"The item someone tries to order suddenly doesn't exist anymore in the database (stock) because another app updated it (or is this not possible because of the mutex?)... a prevention that half of the processing is done and then 1 failed."

Here is the fundamental difference between memory locks and database consistency:

Mechanism Scope Survivability What It Protects
sync.Mutex Single process in RAM Lost if process restarts or crashes Internal Go memory data races between goroutines
Database Transaction (ACID) Entire system (across all server replicas) Durable on disk / storage engine Business consistency (stock count, balance, task state)

If two customers simultaneously purchase the last pair of sneakers through two different web server pods, their local Go mutexes cannot see each other! The database itself must be the authority enforcing atomicity and isolation.

2. The Canonical Go Transaction Idiom

In Go's standard library database/sql, transactions follow a precise, battle-tested pattern:

tx, err := db.BeginTx(ctx, nil)
if err != nil {
    return fmt.Errorf("begin transaction: %w", err)
}
// 💡 THE GOLDEN IDIOM: Always defer a Rollback immediately!
defer tx.Rollback()

// ... Execute queries against tx (not db!) ...
if _, err := tx.ExecContext(ctx, query, args...); err != nil {
    return fmt.Errorf("exec step: %w", err) // Automatically rolls back on return!
}

// All steps succeeded, so commit!
if err := tx.Commit(); err != nil {
    return fmt.Errorf("commit transaction: %w", err)
}
// If Commit() succeeded, the deferred Rollback() safely does nothing!

Why defer tx.Rollback() is brilliant:

  1. If any statement fails and returns early, the deferred Rollback() immediately cancels all changes.
  2. If your code encounters a panic, the deferred Rollback() still runs, preventing dangling locks in the database.
  3. If tx.Commit() succeeds, the transaction is already closed; Go's database driver makes the subsequent deferred tx.Rollback() a harmless no-op that returns sql.ErrTxDone and does nothing.

3. The Real-World Domain: Order Fulfillment & Inventory

Let's ground this in our e-commerce domain. Consider an order where a customer buys an item:

If we do this naively:

  1. Deduct stock in database (Stock: 1 → 0).
  2. Server crashes OR payment processor rejects card.
  3. Result: Stock is gone, customer was not billed, no order exists. Half-done catastrophe!

With an Atomic Transaction:

// 1. Reserve inventory with an atomic condition:
res, err := tx.ExecContext(ctx, "UPDATE inventory SET stock = stock - ? WHERE item_id = ? AND stock >= ?", qty, itemID, qty)
if err != nil {
    return err
}
rows, _ := res.RowsAffected()
if rows == 0 {
    return ErrInsufficientStock // Transaction aborts, stock is untouched!
}

// 2. Insert order task into tasks table:
_, err = tx.ExecContext(ctx, "INSERT INTO tasks (id, payload, status, created_at) VALUES (?, ?, ?, ?)", ...)
if err != nil {
    return err
}

// 3. Commit both together:
return tx.Commit()

4. Preparing for the Outbox Pattern

You noted how you solved this in .NET with Kafka and SQLite. The pattern is called the Transactional Outbox:

[HTTP POST /orders] → [BEGIN TX] → (1. Reserve Stock + 2. Insert Outbox Event) → [COMMIT TX]

↓

[Background Worker] ← Reads pending outbox events from DB → Sends to Queue

Because the business data and the task event are committed in the same atomic transaction, it is physically impossible to save the order without also saving the event to be processed!
