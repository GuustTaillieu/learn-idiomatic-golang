Lesson 0001: Channels, Mutexes, and the Submit Method

Target: Master why and how we protect state and enqueue work in Go.

Mission Link: Building our Concurrent Task Queue Service (MISSION.md). You already wrote the struct in internal/queue/queue.go! Now we implement the method that accepts tasks.

1. Mental Model: What is the Mutex actually protecting?

You asked: "the basic usecase of a mutex is to prevent race conditions (i think right?)"

Yes, exactly! But specifically: a mutex protects shared memory access. In our Queue struct, we have:

type Queue struct {
    mu     sync.RWMutex
    closed bool
    tasks  chan Task
    // ...
}

Here is the critical insight: Channels are already concurrency-safe internally! You do not need a mutex to send to or receive from a channel.

So why do we have mu sync.RWMutex here?

Because of q.closed! If one goroutine calls Shutdown() (which writes q.closed = true) while another goroutine is calling Submit() (which reads if q.closed), that simultaneous read and write is a data race. Go's runtime will detect this and crash if run with -race.

Furthermore, in Go, sending to a closed channel causes a panic! So checking whether the queue is closed before accepting work is essential.

2. Why sync.RWMutex instead of sync.Mutex?

A normal Mutex allows only 1 reader OR 1 writer at any time. But Submit() only reads q.closed — it does not change it. Many goroutines should be allowed to submit tasks at the exact same moment.

  • q.mu.RLock() and defer q.mu.RUnlock(): Multiple goroutines can hold a read lock at once.
  • When shutting down later, q.mu.Lock() will wait until all active submissions are done, then exclusively flip closed = true.

3. Enqueuing Work: The Channel & The Context

In senior Go, any operation that can block or take time takes ctx context.Context as its first parameter:

func (q *Queue) Submit(ctx context.Context, task Task) error

Why? What if our channel buffer (size 100) is completely full? In Go, q.tasks <- task will block until a worker reads a task. But what if the caller wants to abort if it takes more than 500ms, or if the client disconnects?

This is where the select statement shines:

select {
case q.tasks <- task:
    // Success: task enqueued!
case <-ctx.Done():
    // Caller gave up or timed out!
}
