1. The Primary Key Conflict (Why We Need Upsert)

In task_sqlite.go, your query is:

INSERT INTO tasks (id, payload, status, created_at)
VALUES (?, ?, ?, ?);

Think about our task lifecycle:

  1. HTTP handler creates task → calls store.Save(ctx, task) (status is PENDING). Row inserted successfully!
  2. Background worker picks up task → sets task.Status = StatusRunning → calls store.Save(ctx, task).
  3. CRASH: UNIQUE constraint failed: tasks.id! Because the task ID already exists in the table!

In SQLite and PostgreSQL, the senior solution is an Upsert (Insert or Update):

INSERT INTO tasks (id, payload, status, created_at)
VALUES (?, ?, ?, ?)
ON CONFLICT(id) DO UPDATE SET
    status = excluded.status;

If the ID is new, it inserts. If the ID exists, it updates the status! Zero errors.

3. Preventing Half-Done Work: The Go Transaction Idiom

You asked: "How do we prevent things from being half-done? If one part succeeds and the other fails?"

In Go, we use Database Transactions. Here is the canonical, idiomatic Go transaction pattern:

tx, err := db.BeginTx(ctx, nil)
if err != nil {
    return err
}
// 💡 Senior Pattern: Always defer a Rollback immediately!
defer tx.Rollback()

// Step 1: Check and reserve stock
if _, err := tx.ExecContext(ctx, "UPDATE inventory SET stock = stock - 1 WHERE item = ? AND stock > 0", item); err != nil {
    return err // defer tx.Rollback() runs automatically!
}

// Step 2: Record order task
if _, err := tx.ExecContext(ctx, "INSERT INTO tasks ...", ...); err != nil {
    return err // defer tx.Rollback() runs automatically!
}

// Step 3: Commit!
if err := tx.Commit(); err != nil {
    return err
}
// If tx.Commit() succeeded, the deferred tx.Rollback() is a safe no-op!

If anything returns early with an error, the deferred tx.Rollback() guarantees that no half-done state ever reaches the database.
