Lesson 0009: The _test Package & Solving Import Cycles

Target: Learn Go's built-in solution for test import cycles: Black-Box testing with package foo_test.

Your Question: "I have put this in a new package because I got warnings about cyclic imports when I put it in the queue package. You said write this: store.NewMemoryStore() but that created the cyclic import warning. Tell me how to do it properly."

1. Why the Cyclic Import Happened

Look at what was happening:

internal/store/memory.go  ──►  imports "internal/queue" (needs *queue.Task)
             ▲                              │
             │                              ▼
             └────── imports "internal/store" (in queue_test.go with 'package queue')

When queue_test.go had package queue at the top, the compiler treated it as part of package queue. And since internal/store already imports internal/queue, having package queue import internal/store created an illegal loop!

2. Go's Secret Weapon: package <name>_test

In almost any other programming language, all files in the same directory must belong to the exact same package. Go has one deliberate, built-in exception to this rule for testing:

A test file in internal/queue/ is allowed to declare:

package queue_test

Notice the _test suffix!

When the Go compiler sees package queue_test:

  1. It treats queue_test.go as an external client/consumer of the queue package.
  2. It can import both internal/queue and internal/store simultaneously with ZERO import cycle!
  3. The file still lives right next to queue.go in internal/queue/queue_test.go. You do not need an unnatural internal/tests/ folder.

White-Box vs. Black-Box Testing

  • package queue (White-Box): The test is "inside" the package. It can access unexported fields like q.closed, q.tasks, or q.mu.
  • package queue_test (Black-Box): The test is "outside" the package. It interacts only through the exported API (queue.NewQueue, q.Submit, q.Start, q.Stop). This is the gold standard for integration and API testing in Go.

3. Reviewing Your New 3rd Test

Look at lines 53–57 in your new test:

q.Start(ctx, 3)
for i := 0; i < 5; i++ {
    q.Submit(ctx, queue.NewTask("payload"))
    q.Stop() // ⚠️ Inside the loop!
}

Look where q.Stop() is! On iteration i = 0, the first task is submitted, and then q.Stop() shuts down the queue. On iterations 1, 2, 3, 4, q.Submit returned ErrQueueClosed, which wasn't checked.

Moving q.Stop() after the loop will submit all 5 tasks and wait for all 5 to be stored as StatusCompleted!
