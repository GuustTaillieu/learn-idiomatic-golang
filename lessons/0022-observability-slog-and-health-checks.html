1. Answering Your Question: Is s Really How People Name in Go?

Yes, absolutely! In Go, method receivers are almost always 1 or 2 letters:

  • func (s *OrderSqliteStore) Save(...) → s for Store.
  • func (q *Queue) Submit(...) → q for Queue.
  • func (h *Handler) Routes(...) → h for Handler.

Why? In languages like Java or C#, you type this.orderStore.save(...). In Go, the receiver name is intentionally tiny because every method already lives inside that type's namespace! Having s.db or q.orders is concise and reduces reading fatigue.

When should a name be longer? Follow Rob Pike's golden rule: Length is proportional to scope. A variable used across 30 lines should be pendingOrders, while an iterator variable in a 2-line loop is simply order or o.

2. Production Health Checks: /healthz vs /readyz

In cloud deployments (Kubernetes, AWS ECS, GCP Cloud Run), your container needs to communicate its status to load balancers:

1. Liveness (GET /healthz)

Question: "Is the process alive or deadlocked?"

If the Go server is running and can respond to HTTP, return 200 OK. If it hangs or deadlocks, the load balancer kills and restarts the container.

2. Readiness (GET /readyz)

Question: "Can the process actually do work right now?"

Checks downstream dependencies: e.g. db.PingContext(ctx). If the database is locked or migrating, return 503 Service Unavailable so traffic is paused without killing the app!

3. Contextual Structured Logging with slog.With

Instead of manually typing "order_id", order.ID in every single log statement throughout a function, senior Go engineers create a contextual logger:

// Create a logger scoped to this specific order:
logger := slog.With(
    slog.String("order_id", order.ID.String()),
    slog.String("item_id", order.ItemID.String()),
)

// Now every downstream log automatically includes order_id and item_id!
logger.Info("validating stock")
logger.Info("contacting payment gateway")
logger.Error("payment failed", "error", err)

Your Hands-On Challenge: Build Health Probes

  1. In internal/httpapi/handler.go:
    • Add an interface for health checking: 
      type HealthChecker interface {
    Ping(ctx context.Context) error
}
    • Accept an optional HealthChecker (or pass your *sql.DB / store) into NewHandler.
    • Register routes in Routes():
      • GET /healthz: returns 200 OK {"status": "alive"}.
      • GET /readyz: calls checker.Ping(ctx). If nil, returns 200 OK {"status": "ready"}. If error, returns 503 Service Unavailable!
  2. In internal/httpapi/handler_test.go: Write two quick tests:
    • TestHandler_Healthz: verifies GET /healthz returns 200.
    • TestHandler_Readyz: verifies GET /readyz returns 200 on healthy database, and 503 on disconnected database.
