Lesson 0018: Strongly-Typed IDs with sql.Scanner & driver.Valuer

Target: Learn how senior Go engineers build compile-time type safety with custom ID types and teach database/sql how to read and write them natively.

Senior Review: You Are Writing Enterprise-Grade Go!
  • 🏆 You built a Saga Pattern! In internal/processor/multi.go, you collected rollback closures and executed them in reverse order on error. That is production-level distributed compensation logic.
  • 🛡️ Strongly-Typed IDs: Creating type OrderID uuid.UUID and type ItemID uuid.UUID is not overkill. It is a prized pattern that eliminates entire classes of silent ID-swapping bugs at compile time!
  • 💡 Why SQL Complained: SQLite didn't fail because it can't handle custom types—it failed because it didn't know how to serialize a 16-byte array without two standard library interfaces: driver.Valuer and sql.Scanner.

1. Is Strongly-Typed IDs Overkill?

Imagine this common function in a large codebase:

func TransferItem(itemID, targetWarehouseID, requesterID string) error

What happens if someone accidentally calls:

TransferItem(requesterID, itemID, targetWarehouseID) // 💥 All strings! Compiles without error!

The compiler is helpless. In production, this causes corrupt records, security breaches, or missing items.

With Strongly-Typed IDs (The NewType Pattern):

type ItemID uuid.UUID
type WarehouseID uuid.UUID
type UserID uuid.UUID

func TransferItem(item ItemID, warehouse WarehouseID, requester UserID) error

If you swap any arguments, the Go compiler refuses to compile with a clear type mismatch error. Senior Go codebases at Uber, Stripe, and Google use this pattern extensively.

2. The SQL Bridge: driver.Valuer & sql.Scanner

When you ran your tests, you hit this error:

sql: converting argument $1 type: unsupported type domain.ItemID, a array

Why? Because uuid.UUID is under the hood type UUID [16]byte. The standard database/sql driver only knows primitive types: int64, float64, bool, []byte, string, time.Time, and nil.

To teach database/sql how to read and write your custom types, Go provides two canonical interfaces:

1. Writing to DB: driver.Valuer

Package: database/sql/driver

Tells db.ExecContext or db.QueryRowContext how to turn your custom Go type into an SQL primitive.

// Value implements driver.Valuer
func (id ItemID) Value() (driver.Value, error) {
    return uuid.UUID(id).String(), nil
}

2. Reading from DB: sql.Scanner

Package: database/sql

Tells row.Scan(&order.ID) how to convert database bytes/strings into your custom Go type.

// Scan implements sql.Scanner
func (id *ItemID) Scan(src any) error {
    if src == nil {
        *id = NilItemID
        return nil
    }
    switch v := src.(type) {
    case string:
        u, err := uuid.Parse(v)
        if err != nil { return err }
        *id = ItemID(u)
        return nil
    case []byte:
        u, err := uuid.Parse(string(v))
        if err != nil { return err }
        *id = ItemID(u)
        return nil
    default:
        return fmt.Errorf("cannot scan %T into ItemID", src)
    }
}

3. The Magic Result in Your Stores

Once ItemID and OrderID implement driver.Valuer and sql.Scanner:

  1. You can pass order.ID directly into db.ExecContext(ctx, query, order.ID, ...) without calling .String()!
  2. You can scan directly into row.Scan(&order.ID, &order.ItemID, ...) with zero temporary string variables!

4. Watch Out for PlaceOrderProcessor Nil Pointer

In internal/processor/place_order.go:

type PlaceOrderProcessor struct {
    db *sql.DB // ⚠️ Look here!
    InventoryStore InventoryStore
    OrderStore     OrderStore
}

func NewPlaceOrderProcessor(inventoryStore InventoryStore, orderStore OrderStore) *PlaceOrderProcessor {
    return &PlaceOrderProcessor{
        InventoryStore: inventoryStore,
        OrderStore:     orderStore,
    } // db is nil! Calling p.db.BeginTx() will panic!
}

If you plan to use p.db.BeginTx inside PlaceOrderProcessor, pass db *sql.DB into its constructor, or recall our earlier lesson: keep the database transaction inside the store (e.g. OrderStore.CreateOrderWithStockReservation) so processors don't need raw SQL handles!
