1. The Vulnerability in Direct HTTP Submission

Look closely at how an order is created today in handle_create_order.go:

order := domain.NewOrder(req.ItemID, req.Amount)

// 1. Save to DB
if err := h.store.Save(r.Context(), order); err != nil { ... }

// 2. Submit to in-memory channel
if err := h.queue.Submit(r.Context(), order); err != nil { ... }

Think about what happens under extreme real-world load (e.g. Black Friday):

  1. Your channel buffer is 100. Suddenly, 500 requests hit your HTTP API simultaneously.
  2. Once the 100 slots in q.orders are full, q.orders <- order blocks!
  3. Now, 400 incoming HTTP requests are frozen, holding open TCP sockets, tying up database connections, and timing out clients.
  4. If you restart the server, you rely on the startup sweeper to catch up. But while running, your HTTP ingestion is coupled to worker processing speed.

2. The Enterprise Solution: The Transactional Outbox

How do Stripe, Uber, and high-scale systems decouple ingestion from processing?

[Client] → (POST /orders) → [DB Transaction: INSERT order (PENDING)] → Returns 202 Accepted!

↓ (Completely decoupled in background)

[Outbox Dispatcher Goroutine] → Polls DB for PENDING → Pushes to Worker Queue → Updates to DISPATCHED

The Architectural Superpowers:

  • Zero Ingestion Latency: The HTTP handler only inserts one row into SQLite and immediately returns 202 StatusAccepted. It never blocks on channel capacity or slow workers!
  • True Durability: Even if workers are completely offline or 10,000 orders arrive at once, every single order is safe on disk in the database.
  • Crash Resilient by Design: If the server restarts, crashes, or scales up, the Outbox Dispatcher simply resumes reading from the database. No special boot-sweeper needed!

3. Building the Outbox Dispatcher in Go

A background dispatcher in Go uses a time.Ticker and a cancellation select:

func (d *OutboxDispatcher) Start(ctx context.Context) {
    ticker := time.NewTicker(500 * time.Millisecond)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            d.dispatchBatch(ctx)
        }
    }
}

Inside dispatchBatch:

  1. Fetch up to $N$ orders with status = 'PENDING' (e.g. LIMIT 50).
  2. For each order:
    • Push into queue.Submit (or mark StatusRunning / StatusDispatched).
