Target: Fix a subtle phantom-rollback bug, eliminate leftover SQL scan boilerplate, and build a boot-time recovery sweeper to guarantee zero lost orders across crashes.

1. Critical Bug: The Phantom Rollback in PlaceOrderProcessor

Look closely at how you returned from Process in internal/processor/place_order.go:

// ⚠️ Look at the return statement:
return func() error {
    if err := p.InventoryStore.ReleaseStock(ctx, stock); err != nil {
        return err
    }
    return nil
}, tx.Commit()

The Gotcha: What happens if tx.Commit() returns an error (e.g., SQLite locked or disk I/O error)?

  1. Go evaluates both return values: the rollback closure func() error AND the error from tx.Commit().
  2. In queue.go, the worker sees err != nil. It dutifully calls cleanup()!
  3. cleanup() calls ReleaseStock(ctx, stock) which runs UPDATE inventory SET quantity = quantity + 1.
  4. The Catastrophe: Because tx.Commit() failed, the stock deduction was already rolled back by the deferred tx.Rollback()! When cleanup() runs, you add +1 stock to an item that was never deducted! You just created free phantom stock out of thin air.

The Fix: Never return a rollback function if the commit itself failed!

if err := tx.Commit(); err != nil {
    return nil, fmt.Errorf("failed to commit order transaction: %w", err)
}

rollbackFunc := func() error {
    return p.InventoryStore.ReleaseStock(ctx, stock)
}
return rollbackFunc, nil

2. Code Cleanup: Delete the Redundant SQL Parsing

Now that domain.ItemID implements sql.Scanner, you no longer need the temporary string variables in internal/store/inventory_sqlite.go:

// Before:
var itemIDStr string
if err := row.Scan(&itemIDStr, &stock.Quantity, &stock.CreatedAt, &stock.UpdatedAt); err != nil { ... }
itemUUID, err := uuid.Parse(itemIDStr)
stock.ItemID = domain.ItemID(itemUUID)

// After (Idiomatic Senior Go):
if err := row.Scan(&stock.ItemID, &stock.Quantity, &stock.CreatedAt, &stock.UpdatedAt); err != nil {
    if errors.Is(err, sql.ErrNoRows) {
        return nil, fmt.Errorf("stock not found for item %s: %w", itemID, err)
    }
    return nil, fmt.Errorf("failed to get stock: %w", err)
}

Also, in ReserveStock, replace stock.ItemID.String() with simply stock.ItemID. The driver will automatically call .Value().

3. DRY Up MultiProcessor

In internal/processor/multi.go, you wrote the exact same reverse-loop rollback closure twice (once in the error branch, once in the success branch). You can extract it into a local closure:

rollbackAll := func() error {
    for i := len(rollbackFuncs) - 1; i >= 0; i-- {
        if err := rollbackFuncs[i](); err != nil {
            return fmt.Errorf("rollback failed: %w", err)
        }
    }
    return nil
}

// On error:
return rollbackAll, err

// On success:
return rollbackAll, nil

4. The Next Frontier: Crash Recovery & Sweepers

Consider this real-world production incident:

"A server receives 200 orders. The HTTP handler writes them into SQLite with status PENDING and queues them. Suddenly, someone trips over the power cable in the datacenter, or Docker restarts the container."

When your app reboots:

  • The in-memory Go channel (q.orders) is completely empty!
  • Those 200 orders exist in SQLite with status = "PENDING", but will never be processed because nothing pushes them into the channel!

This is where senior Go systems implement a Boot Recovery Sweeper.

When main.go boots up (before opening the HTTP port to traffic), it queries the database for stranded orders and feeds them into the queue:

// At startup:
pendingOrders, err := orderStore.GetPendingOrders(ctx)
for _, order := range pendingOrders {
    _ = q.Submit(ctx, order)
}
