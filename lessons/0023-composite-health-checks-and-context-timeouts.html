Lesson 0023: Deep Health Checks & The Composite Health Pattern

Target: Evaluate queue-based health checks vs. database probes, and master composite health checking with context timeouts.

Review of Your Implementation:
  • 🎉 All tests passing! GET /healthz and GET /readyz routes are working cleanly.
  • ✨ Interface Decoupling: In handler.go, type HealthChecker interface { Ping(ctx context.Context) error } perfectly decouples your HTTP API from whatever does the checking!
  • 🤔 Your Question: "I turned the Queue into the health checker.. idk if that was a good option?" Let's analyze it!

1. Is Turning the Queue into the Health Checker a Good Option?

The Good:

  • It verifies that the queue is not closed (q.closed == false). If the service is shutting down (graceful shutdown in progress), Ping() returns ErrQueueClosed, signaling load balancers to stop sending new traffic! That is a great senior intuition.

The Blind Spot:

  • When a client sends POST /orders, what is the very first thing the server touches? The Database! (h.store.Save(ctx, order)).
  • If the SQLite file is locked, the disk is full, or the database connection is broken:
    • queue.Ping() will happily return nil (because in-memory RAM mutexes are fine).
    • GET /readyz will report 200 OK ("ready").
    • Load balancers will keep sending users to this server pod, and 100% of customer orders will crash with HTTP 500!

2. The Gold Standard: The Composite Health Checker

Why choose between checking the Queue or checking the Database when you can check both?

Remember how we used the Composite Pattern for MultiProcessor? We can use the exact same pattern for health checks!

type MultiHealthChecker struct {
    checkers []HealthChecker
}

func NewMultiHealthChecker(checkers ...HealthChecker) *MultiHealthChecker {
    return &MultiHealthChecker{checkers: checkers}
}

func (m *MultiHealthChecker) Ping(ctx context.Context) error {
    for _, c := range m.checkers {
        if err := c.Ping(ctx); err != nil {
            return err // Fails fast if ANY critical dependency is down!
        }
    }
    return nil
}

And for the database, a tiny adapter struct:

type DBHealthChecker struct {
    db *sql.DB
}

func (d *DBHealthChecker) Ping(ctx context.Context) error {
    return d.db.PingContext(ctx)
}

3. The Timeout Rule for Health Probes

In cloud deployments, health probes run every few seconds. If a database hangs, you must not let GET /readyz hang indefinitely holding open sockets.

Senior Go health handlers always enforce a strict timeout:

func (h *Handler) handleReady(w http.ResponseWriter, r *http.Request) {
    // 💡 Enforce a 2-second deadline on dependency checks:
    ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
    defer cancel()

    if err := h.healthChecker.Ping(ctx); err != nil {
        http.Error(w, "Service Unavailable", http.StatusServiceUnavailable)
        return
    }
    // ...
}
