1. Connecting to Frontends: gRPC vs. WebSockets vs. SSE

You asked an essential architectural question: "What is the best way to connect a Go backend to a frontend? What about gRPC?"

Technology How It Works Best Production Use Case
gRPC Protobuf over HTTP/2. Strict RPC contracts. ✅ Backend-to-Backend microservices.
❌ Clunky for web browsers (requires Envoy proxy + grpc-web JS runtime).
WebSockets Full-duplex (2-way) TCP socket over HTTP upgrade. ✅ 2-way real-time apps: multiplayer gaming, collaborative whiteboards, live chat.
⚠️ Requires custom heartbeat ping-pongs and reconnect logic.
Server-Sent Events (SSE) Standard HTTP streaming. Unidirectional (Server → Client). 🏆 The industry standard in Go for order tracking, live metrics, and AI token streaming (ChatGPT, Claude).
✅ Built into browsers with native new EventSource('/api/events').
✅ Works over plain HTTP/1.1 and HTTP/2 without extra proxies!

2. The Core of Go: io.Writer and http.Flusher

In Go, everything that outputs bytes implements the io.Writer interface:

type Writer interface {
    Write(p []byte) (n int, err error)
}

Your HTTP response handler receives w http.ResponseWriter. Behind the scenes, w is an io.Writer! When you write data to w, the Go HTTP server buffers it in memory to send a single efficient TCP packet.

The Streaming Dilemma: In real-time streaming, you cannot wait for the buffer to fill up! You must push the data across the internet immediately. That is where http.Flusher comes in:

flusher, ok := w.(http.Flusher)
if !ok {
    http.Error(w, "Streaming unsupported", http.StatusInternalServerError)
    return
}

// 1. Write the SSE formatted message:
fmt.Fprintf(w, "data: %s\n\n", jsonPayload)

// 2. Force Go to push the packet over the wire immediately!
flusher.Flush()

3. Advanced Channel Pattern: The Pub-Sub Event Hub

When an order transitions from PENDING → PROCESSING → COMPLETED inside your worker queue, how do multiple connected browser tabs receive the notification?

Worker Queue: hub.Broadcast(OrderEvent{ID, Status})

↓

Event Hub: Iterates over connected client channels

↓

Client A Channel → HTTP Goroutine A → SSE → Browser Tab 1

Client B Channel → HTTP Goroutine B → SSE → Browser Tab 2

Senior Safeguard: The Non-Blocking Send

What happens if Client A is on a slow 3G connection and stops reading? If you do a normal send (ch <- event), your entire worker pool will block and freeze waiting for Client A!

In production Go, you always protect the server with a non-blocking channel send:

select {
case ch <- event: // Sent successfully!
default:          // Client buffer is full! Drop the message so the server stays fast!
}
