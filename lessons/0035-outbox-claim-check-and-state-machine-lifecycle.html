Lesson 0035: The Outbox Claim Check, State Machine Lifecycle, & Race-Free Persistence

Target: Fix the outbox infinite loop properly, understand why lifecycle state transitions must never run in a parallel saga, and guarantee bulletproof state consistency.

Brilliant Detective Work! 🕵️

You observed the exact runtime bug that plagues junior engineers in asynchronous architectures:

"First it kept on running because the order was still marked as pending so I added a processor that marks it as running. But this would probably have issues when the processes fails or something right?"

You diagnosed the root cause and correctly suspected the race/failure flaws of putting state mutation into a parallel processor! Let's explore the battle-tested senior solution.

1. Why the Infinite Loop Happened

Every 500 milliseconds, OutboxDispatcher runs:

pendingOrders, _ := d.orderStore.GetPendingOrders(ctx) // SELECT WHERE status = 'PENDING'
for _, order := range pendingOrders {
    d.queue.Submit(ctx, order)
}

Because submitting an order to an in-memory queue channel does not alter SQLite, 500ms later GetPendingOrders queries SQLite again, sees the exact same order still marked PENDING, and submits it again! This repeats infinitely.

2. Why OrderMarker in Parallel Has Flaws

You created OrderMarker and wired it into processor.NewParallel(p1, p2, p3). Why is this dangerous in production?

A. Concurrent Database Write Race

Parallel uses errgroup to execute steps simultaneously on separate CPU threads. OrderMarker and OrderPlacing will both execute UPDATE orders on the exact same row in SQLite at the exact same millisecond, fighting for database locks and overwriting each other!

B. Sibling Failure Orphans the State

If OrderPlacing fails (e.g. out of stock), but OrderMarker succeeded, what is the order's status? If the rollback fails or doesn't execute cleanly, the database row stays stuck in RUNNING forever.

C. Architectural Separation of Concerns

A Pipeline Step represents business domain actions (e.g. reserve inventory, charge stripe).
A Lifecycle State Transition represents the orchestrator's contract (e.g. PENDING → RUNNING → COMPLETED). They belong at different layers!

3. The Industry Standard: The 3-Step Lifecycle

Step 1: Claim at Dispatch (in OutboxDispatcher)

Before putting the order into the worker channel, the dispatcher claims it by transitioning it in SQLite:

func (d *OutboxDispatcher) DispatchOnce(ctx context.Context) error {
    pendingOrders, err := d.orderStore.GetPendingOrders(ctx)
    if err != nil {
        return err
    }

    for _, order := range pendingOrders {
        // 1. Claim in SQLite: PENDING -> RUNNING
        order.Status = domain.OrderStatusRunning
        if err := d.orderStore.Save(ctx, order); err != nil {
            return err
        }

        // 2. Submit to worker channel
        if err := d.queue.Submit(ctx, order); err != nil {
            return err
        }
    }
    return nil
}

On the very next tick 500ms later, GetPendingOrders (which queries status = 'PENDING') will skip this order completely. No infinite loop!

Step 2: Atomic Success in the Transaction (in OrderPlacing)

When stock deduction succeeds, save the completed order inside the same database transaction before calling tx.Commit():

// Inside OrderPlacing.Process:
order.Status = domain.OrderStatusCompleted
if err := p.OrderStore.Save(txCtx, order); err != nil {
    return nil, fmt.Errorf("failed to save completed order: %w", err)
}

if err := tx.Commit(); err != nil {
    return nil, fmt.Errorf("failed to commit: %w", err)
}

Stock deduction and order completion succeed or fail together as a single atomic unit.

Step 3: Clean Rollback on Failure

If the payment fails or stock is exhausted, the rollback function marks the order as FAILED and saves it to SQLite:

return func() error {
    _ = p.InventoryStore.ReleaseStock(ctx, stock)
    order.Status = domain.OrderStatusFailed
    return p.OrderStore.Save(ctx, order)
}, nil
