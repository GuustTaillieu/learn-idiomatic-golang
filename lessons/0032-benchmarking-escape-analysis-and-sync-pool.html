1. What Separates Senior Go Engineers: Mechanical Sympathy

In many languages, performance is an afterthought or left to JIT compilers. In Go, senior engineers write code with mechanical sympathy: understanding how the Go runtime, heap allocator, and CPU caches interact.

The Silent Killer: Garbage Collector (GC) Pressure

Every time you allocate memory on the heap (e.g. creating slices, closures, or new buffers with &bytes.Buffer{}):

  1. The runtime must find free memory blocks.
  2. When heap size reaches a threshold, the Go GC triggers a concurrent sweep.
  3. Under heavy production traffic (10,000 req/sec), thousands of allocations cause CPU spikes and latency jitter (p99 tail latency).

2. Measuring Reality: testing.B & -benchmem

Go has benchmarking built right into the standard testing package. Senior engineers never guess; they measure:

func BenchmarkOrderSerialization(b *testing.B) {
    order := domain.NewOrder(domain.ItemID(uuid.New()), 10)

    b.ResetTimer()
    b.ReportAllocs() // 💡 Tracks exact bytes and allocation count!

    for b.Loop() { // Go 1.24+ idiomatic loop (or for i := 0; i < b.N; i++)
        _ = serializeOrder(order)
    }
}

Run your benchmarks from the terminal:

go test -bench=BenchmarkOrderSerialization -benchmem ./...

You will see output like:

BenchmarkOrderSerialization-8    2000000    612.4 ns/op    512 B/op    4 allocs/op

3. Escape Analysis: Stack vs. Heap

How do you know why a variable is being allocated on the heap? Ask the compiler!

go build -gcflags="-m" ./internal/domain/...

The compiler will tell you:

  • "... escapes to heap" → Allocated on heap (slow, GC overhead).
  • "... does not escape" → Allocated on CPU stack (virtually instant, zero GC).

4. The Secret Weapon: sync.Pool for Zero-Allocation Hot Paths

When you need temporary buffers or objects repeatedly in worker pools or HTTP handlers, instead of creating a new one on every request, you recycle them using sync.Pool:

var bufPool = sync.Pool{
    New: func() any {
        return new(bytes.Buffer)
    },
}

func FastSerialize(order *domain.Order) []byte {
    // 1. Borrow from pool (no heap allocation if pool has available buffers!)
    buf := bufPool.Get().(*bytes.Buffer)
    // 2. CRITICAL: Reset before use, so previous data doesn't leak!
    buf.Reset()
    // 3. Put back when done
    defer bufPool.Put(buf)

    // Write data into buf...
    return buf.Bytes()
}

Result: 4 allocations and 512 B/op drop to 0 B/op and 0 allocs/op!
