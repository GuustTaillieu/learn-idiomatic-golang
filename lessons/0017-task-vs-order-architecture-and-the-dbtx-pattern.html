Lesson 0017: Task vs. Order Architecture & The DBTX Pattern

Target: Master the architectural boundary between generic Job Queues and Domain Models, and learn the senior Go DBTX pattern for sharing transactions across stores.

First: Give Yourself Credit!

You did not mess up. In fact, you naturally gravitated toward Domain-Driven Design (DDD) and immediately discovered the single most famous architectural dilemma in relational database engineering (the Transaction-Scope Problem)! You are thinking like an architect, not just a syntax typist.

1. Why was it called Task? (Infrastructure vs. Domain)

You asked: "What was the meaning of the name Task? Why not Order from the start?"

In senior backend architecture, there are two distinct layers:

1. Generic Infrastructure Layer

Example: Redis Celery, RabbitMQ, AWS SQS, or our queue.Queue.

A queue in production does not only process orders. It processes:

  • TaskType: "SEND_WELCOME_EMAIL"
  • TaskType: "ENCODE_MP4_VIDEO"
  • TaskType: "GENERATE_MONTHLY_INVOICE"
  • TaskType: "PROCESS_ORDER"

Because the queue is a reusable engine, it calls its units of work a Task (or Job). It contains generic metadata: ID, Payload []byte, Retries, Status.

2. Business Domain Layer

Example: Your e-commerce fulfillment app.

This layer knows nothing about worker pools or channels. It cares about:

  • Order (customer, item, price, status)
  • Inventory (SKU, stock count)
  • Payment (credit card token, authorization)

When a customer buys sneakers, the HTTP handler creates an Order in the DB, and enqueues a Task whose payload is {"order_id": "123"}.

Verdict on your rename: Making a specialized Order queue is completely fine for a dedicated Order Service! But keeping the queue generic (Task) allows the same worker queue to be reused for emails, pdf generation, and inventory sync. In senior Go, we usually keep internal/queue generic and put our business logic in internal/domain.

2. The Transaction Dilemma: db.ExecContext vs. tx.ExecContext

In your SafeDBMultiProcessor, you wrote this brilliant attempt:

func (m *SafeDBMultiProcessor) Process(ctx context.Context, itemID uuid.UUID, amount int) error {
    tx, err := m.db.BeginTx(ctx, nil)
    if err != nil { return err }
    defer tx.Rollback()

    for _, p := range m.processors {
        if err := p.Process(ctx, itemID, amount); err != nil {
            return fmt.Errorf("pipeline step failed: %w", err)
        }
    }
    return tx.Commit()
}

Then you stopped and noticed: "Wait! Inside ReserveStock, it calls s.db.ExecContext(...), not tx.ExecContext(...)! The sub-processors aren't actually participating in the transaction!"

You hit the nail on the head. If a store method executes against s.db, it runs on its own isolated connection outside the transaction!

How Senior Go Engineers Solve This: The DBTX Pattern

Notice that both *sql.DB and *sql.Tx have the exact same query methods: ExecContext, QueryContext, and QueryRowContext.

Senior Go code abstracts this into a tiny 3-method interface (this is the exact pattern generated by the industry-standard tool sqlc):

// DBTX is satisfied by BOTH *sql.DB and *sql.Tx!
type DBTX interface {
    ExecContext(ctx context.Context, query string, args ...any) (sql.Result, error)
    QueryContext(ctx context.Context, query string, args ...any) (*sql.Rows, error)
    QueryRowContext(ctx context.Context, query string, args ...any) *sql.Row
}

Now, your Store doesn't store a hardcoded *sql.DB. It accepts a DBTX, or has a helper method WithTx(tx *sql.Tx):

type InventoryStore struct {
    db DBTX // Can be *sql.DB OR *sql.Tx!
}

// WithTx returns a lightweight copy of the store scoped to a transaction!
func (s *InventoryStore) WithTx(tx *sql.Tx) *InventoryStore {
    return &InventoryStore{db: tx}
}

3. The Non-DB Reality: The "Saga" Problem

There is a second critical insight seniors understand about pipelines:

What happens when Step 1 is "Reserve Stock in SQLite", Step 2 is "Charge Credit Card via Stripe API", and Step 3 is "Send Email via SendGrid"?

You cannot wrap a Stripe HTTP call in an SQLite transaction!

  • If SendGrid fails, SQLite can rollback the stock, but Stripe already charged the customer's real money!

This is why in real production distributed systems, we do not try to run an entire multi-step pipeline inside a single database transaction. Instead:

  1. Database transactions are used for atomic local state (e.g. creating the order and deducting stock atomically).
  2. Pipelines across services use Compensating Actions (Sagas): if Step 2 (payment) fails, you call inventoryStore.ReleaseStock(...) to undo Step 1!

4. A Sneaky SQL Gotcha: UPDATE Rows Affected

In internal/store/inventory_sqlite.go, you wrote:

_, err := s.db.ExecContext(ctx, query, ...)
if err != nil {
    if errors.Is(err, sql.ErrNoRows) {
        return errors.New("insufficient stock")
    }
    return err
}
⚠️ Gotcha Alert: In Go's database/sql, sql.ErrNoRows is ONLY returned by QueryRowContext(...).Scan(...) when a SELECT returns 0 rows.

An UPDATE statement that matches 0 rows (because quantity < ?) will return err == nil!

To check if the stock was updated, you must inspect the sql.Result: 
res, err := s.db.ExecContext(ctx, query, ...)
if err != nil {
    return err
}
rows, err := res.RowsAffected()
if err != nil {
    return err
}
if rows == 0 {
    return errors.New("insufficient stock") // Zero rows updated!
}

5. How to Put You Back on Track (Clean & Confident)

Let's align your architecture so it feels clean, senior, and crystal clear:

  1. Keep Your Domain: Having internal/domain with Order, Item, and Stock is great domain modeling! Keep it.
  2. Clean Transactional Order Placement: When an order is submitted: 
    tx, err := db.BeginTx(ctx, nil)
defer tx.Rollback()

// 1. Atomically deduct stock (check RowsAffected() == 0)
// 2. Insert the Order as PENDING
// 3. Commit!
tx.Commit()
  3. Pass the Order to the Queue: Once committed safely to SQLite, pass the order to the queue for background asynchronous processing (e.g. sending receipt, notifying warehouse, marking completed)!
