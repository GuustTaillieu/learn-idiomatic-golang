1. Why Did Your Singleflight Test Fail? (Expected 1, Got 10)

Your test assertion failed with:

cached_inventory_test.go:42: expected Get to be called once, but got 10

The Mental Model: What Singleflight Actually Does

singleflight.Group is NOT a persistent cache (like a map or Redis).

It only deduplicates requests that are concurrently in-flight at the exact same moment. The instant the underlying function returns, the key is evicted from the group, and subsequent calls execute normally.

Goroutine 1 calls sf.Do() → Starts mockStore.Get() → Finishes in 10 nanoseconds!

Goroutine 2 starts → Goroutine 1 is ALREADY DONE! → sf.Do() starts again!

In your mock store, Get() did not perform any network or disk I/O; it simply incremented an integer and returned instantly. As a result, the 10 goroutines executed serially one after another. No two goroutines were ever in-flight at the same time!

How Senior Go Engineers Test Singleflight

To test deduplication deterministically, you must ensure two conditions:

  1. Simulated I/O Latency: Make the mock store take some time (e.g. time.Sleep(25 * time.Millisecond)) to keep the operation in-flight.
  2. Synchronized Launch Gate: Instead of launching goroutines in a loop that fires haphazardly, have every goroutine wait on a channel (<-start) before calling Get(). Then close(start) to release all 10 goroutines at the exact same microsecond!

2. The Big Architectural Question: How Should Go Projects Be Structured?

You asked an insightful architectural question:

"would it not be cleaner to do a folder called order which has 'sql_store', 'model', etc., so you write order.SQLStore instead of stores.OrderSQLStore?"

You noticed what every senior Go engineer discovers: Grouping packages by layer (models/, stores/, controllers/) is an anti-pattern in Go!

Why "Package-by-Layer" Hurts in Go:

  1. Stuttering: stores.OrderSQLStore repeats "store" twice.
  2. The Cyclic Dependency Trap: In Go, package cycles (A → B → A) are strictly illegal and fail to compile. Layered packages inevitably try to reference each other as features grow.
  3. Low Cohesion: Modifying a single feature requires hunting through 4 or 5 different folders.

The Two Idiomatic Industry Approaches:

Approach A: Ben Johnson's "Standard Package Layout" (Technology Subpackages)

Used widely in production tools (like BoltDB and HashiCorp projects):

  • internal/domain: Contains pure domain models (Order, Stock) and interface definitions (OrderStore, InventoryStore). No database imports.
  • internal/sqlite: Implements the interfaces using SQLite. 
    package sqlite

type OrderStore struct { db *sql.DB }
func NewOrderStore(db *sql.DB) *OrderStore { ... }
    Look at how this reads to the caller in main.go: 
    import "myproject/internal/sqlite"

orderStore := sqlite.NewOrderStore(db) // ✅ Zero stutter! Clean and expressive!
  • internal/httpapi: Implements the HTTP routes consuming domain.OrderStore.

Approach B: Package-by-Feature (Vertical Slices) — Your Idea!

Used in modular monoliths and microservices:

  • internal/order/: Contains order.go (struct), store.go (persistence), and handler.go (HTTP).
  • Caller reads: order.NewStore(db), order.NewHandler(s).
  • The Crucial Rule: If order needs to coordinate with inventory, they must never import each other directly! An orchestrator (like your processor.PlaceOrderProcessor) imports both and coordinates them.
