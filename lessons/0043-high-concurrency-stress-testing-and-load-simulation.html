Lesson 0043: High-Concurrency Stress Testing & Load Simulation

Target: Put your entire architecture to the test under real load. Build a high-throughput CLI load generator in Go, verify your rate limiter (429s), and observe real-time SSE streaming under pressure.

Review of Your Error Handling Implementation:

You created a category-based error classification system using errors.Join and errors.Is. That is a fantastic mental model! Here is the senior breakdown of what was great and what to watch out for:

  • The Great: Grouping domain errors into categories (ErrNotFound, ErrConflict, etc.) is the exact architectural pattern used by gRPC canonical error codes and RFC 7807 (Problem Details). Adding Order.Validate() enforces invariants before database writes.
  • Leaking HTTP into Domain: ErrBadRequest is an HTTP-specific concept. The domain layer doesn't know it's being invoked over HTTP—it could be a CLI tool, gRPC service, or event consumer! Prefer domain terms like ErrValidation or ErrInvalid.
  • The errors.Unwrap Trap: In respondWithError, you called errors.Unwrap(err) before checking errors.Is(err, ...). errors.Is already walks the entire error chain recursively! Furthermore, errors.Unwrap returns nil on errors created with errors.Join (because joined errors implement Unwrap() []error, not Unwrap() error).
  • The Double-Logging Anti-Pattern: In internal/sqlite/order.go, you logged slog.Error(...) AND returned domain.ErrInternal, which then got logged a second time in respondWithError. In Go: either log an error OR return it—never both.
  • Context Cancellation in Queue: In order_queue.go, returning ErrQueueClosed when ctx.Done() fires tells the caller the queue is closed when in reality the caller's request was cancelled or timed out. Return ctx.Err() instead.

1. Putting Your System to the Test

You've built an incredible system: SQLite storage, transactional outbox, worker queue, SSE streaming, rate limiting, and fail-fast configuration. But how does it behave when 200 orders arrive simultaneously?

Instead of using third-party tools like ApacheBench or k6, senior Go engineers often build custom, lightweight test harnesses using Go's first-class concurrency primitives (goroutines, channels, and sync.WaitGroup).

2. The Architecture of cmd/stress/main.go

package main

import (
    "bytes"
    "context"
    "flag"
    "fmt"
    "net/http"
    "sync"
    "sync/atomic"
    "time"
)

func main() {
    targetURL := flag.String("url", "http://localhost:8080/orders", "Target URL")
    concurrency := flag.Int("c", 10, "Concurrent workers")
    totalRequests := flag.Int("n", 100, "Total requests to send")
    flag.Parse()

    // Dedicated high-throughput HTTP transport
    client := &http.Client{
        Timeout: 5 * time.Second,
        Transport: &http.Transport{
            MaxIdleConns:        500,
            MaxIdleConnsPerHost: 100,
            IdleConnTimeout:     90 * time.Second,
        },
    }

    var (
        successCount atomic.Int64
        rateLimitCount atomic.Int64
        failureCount atomic.Int64
    )

    jobs := make(chan int, *totalRequests)
    for i := 0; i < *totalRequests; i++ {
        jobs <- i
    }
    close(jobs)

    start := time.Now()
    var wg sync.WaitGroup

    for w := 0; w < *concurrency; w++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for range jobs {
                payload := []byte(`{"item_id": "00000000-0000-0000-0000-000000000001", "amount": 1}`)
                resp, err := client.Post(*targetURL, "application/json", bytes.NewReader(payload))
                if err != nil {
                    failureCount.Add(1)
                    continue
                }
                resp.Body.Close()

                switch resp.StatusCode {
                case http.StatusCreated:
                    successCount.Add(1)
                case http.StatusTooManyRequests:
                    rateLimitCount.Add(1)
                default:
                    failureCount.Add(1)
                }
            }
        }()
    }

    wg.Wait()
    duration := time.Since(start)

    fmt.Printf("\n--- Load Test Summary ---\n")
    fmt.Printf("Total Time:     %v\n", duration)
    fmt.Printf("Success (201):  %d\n", successCount.Load())
    fmt.Printf("Limited (429):  %d\n", rateLimitCount.Load())
    fmt.Printf("Failed:         %d\n", failureCount.Load())
    fmt.Printf("Throughput:     %.2f req/s\n", float64(*totalRequests)/duration.Seconds())
}

Your Hands-On Challenge

  1. Create cmd/stress/main.go:
    • Implement the concurrent load generator above with flags for -c (concurrency), -n (total requests), and -url.
    • Use atomic.Int64 for lock-free metrics tracking across worker goroutines.
  2. Start the server in a separate terminal: 
    go run cmd/server/main.go
  3. Open your browser at http://localhost:8080 to see the real-time SSE dashboard.
  4. In another terminal, fire the stress test: 
    go run cmd/stress/main.go -c 15 -n 150
  5. Observe:
    • How many requests were accepted (201) vs rate-limited (429).
    • Watch the dashboard stream order processing events live via SSE.
    • Notice the Outbox dispatcher processing orders in the background.
  6. Run your test suite to ensure all unit tests continue to pass: 
    go test -v -race ./...
