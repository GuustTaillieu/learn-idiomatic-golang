Lesson 0003: Graceful Shutdown, Drain Semantics, and Race Testing

Target: Master clean resource shutdown and verify concurrency with go test -race.

Win: You've built Submit, Start, and worker! Tasks can now be queued and processed across concurrent workers. Now comes the mark of a senior engineer: stopping cleanly without dropping data or deadlocking.

1. What Happens on Shutdown?

In production, when a service receives a shutdown signal (e.g. Ctrl+C or Kubernetes SIGTERM), you cannot just kill the process. Any task currently being processed or sitting in the buffer must be allowed to complete.

A graceful shutdown requires three sequential steps:

  1. Stop accepting new work: Reject future Submit() calls with ErrQueueClosed.
  2. Signal workers that no more work is coming: Close the tasks channel.
  3. Wait for workers to finish: Block until all in-flight tasks are drained and every worker exits.

2. The Exclusive Write Lock (sync.Mutex vs sync.RWMutex)

In Submit(), we used q.mu.RLock() because we were only reading q.closed.

In Shutdown(), we are mutating state (setting q.closed = true and closing the channel). Here, we must acquire the exclusive write lock: q.mu.Lock().

func (q *Queue) Shutdown() {
    q.mu.Lock()
    if q.closed {
        q.mu.Unlock()
        return // Idempotent: already closed!
    }
    q.closed = true
    close(q.tasks)
    q.mu.Unlock()

    q.wg.Wait() // Wait for all workers to finish draining!
}

3. Why close(q.tasks) Doesn't Drop Tasks

A beautiful feature of Go channels: closing a channel does NOT destroy its buffered items.

If there are 5 tasks still in the channel when close(q.tasks) is called, the workers will continue to read them one by one (with ok == true). Only when the channel is completely empty will the next read return ok == false, triggering the worker to exit and call defer q.wg.Done().

4. Why call q.wg.Wait() AFTER releasing the lock?

Notice that we unlock q.mu.Unlock() before calling q.wg.Wait().

If you call Wait() while still holding q.mu.Lock(), any goroutine that might need the lock (even a reader) will be blocked indefinitely while waiting for workers to finish. A golden rule of Go concurrency: hold locks for the shortest possible scope. Never perform blocking operations (like I/O or WaitGroup waiting) while holding a mutex.
