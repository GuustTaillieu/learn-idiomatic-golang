Lesson 0013: Pipeline Concurrency & Preventing "Half-Done" Work

Target: Learn how senior Go engineers fan-out parallel tasks, handle partial failures, and guarantee data consistency.

Milestone: You assembled cmd/server/main.go! Your server starts, manages workers, routes requests, and handles OS interrupts. Now we take this system from a working prototype to an enterprise-grade production architecture.

1. Quick Senior Review of your main.go

In cmd/server/main.go, you wrote:

ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
// ...
case <-ctx.Done():
    srv.Shutdown(ctx) // ⚠️ Look closely at ctx!

The Gotcha: When the user hits Ctrl+C, ctx is already cancelled! If you pass an already-cancelled context to srv.Shutdown(ctx), the HTTP server aborts instantly instead of waiting for active requests to finish.

The Fix: Create a fresh context with a grace timeout for teardown:

shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
_ = srv.Shutdown(shutdownCtx)

2. Answering Your Questions: Real-World Architecture

A. Can an order trigger multiple processors at once?

Yes! This is called Fan-Out Concurrency.

When an order arrives, we want to run independent tasks in parallel:

  • Step 1 (Sequential): Reserve Stock & Charge Payment.
  • Step 2 (Parallel Fan-Out): Once payment is secured:
    • Worker Goroutine 1: Generate PDF receipt.
    • Worker Goroutine 2: Send confirmation email.
    • Worker Goroutine 3: Notify warehouse packing system.

How do we run these in Go? We can compose multiple Processor implementations inside a Composite Processor using goroutines and a sync.WaitGroup!

B. "Can a mutex prevent an item from being out-of-stock?"

No, and this is a vital senior distinction:

  • A Mutex only protects memory inside a single running Go process in RAM.
  • If you run 2 instances of your server in Docker/Kubernetes, Server A's mutex knows nothing about Server B!

To prevent race conditions on shared data across servers, the source of truth must be the Database:

  1. Atomic SQL Transactions (ACID): In SQLite or PostgreSQL, you execute: 
    BEGIN TRANSACTION;
UPDATE inventory SET stock = stock - 1 WHERE item_id = 42 AND stock > 0;
-- If 0 rows updated, stock ran out! Rollback!
ROLLBACK;
  2. Compensating Actions (The Saga Pattern): If credit card payment fails after inventory was reserved, your worker executes a compensating step: inventory.Release(orderID) so the stock is restored!

C. "How do we make sure an order is never lost?"

You mentioned your experience with .NET, SQLite, and Kafka. That industry pattern is called the Transactional Outbox Pattern!

If your server crashes right between saving the order in the database and putting it onto the channel, the order is lost. With the Outbox pattern, you save both the order AND an outbox message inside the same database transaction. When the service reboots, it reads pending outbox messages and resumes processing. Nothing is ever lost!

Your Hands-On Challenge: Build a Composite Processor

Let's make our processing pipeline modular by applying the Composite Pattern:

  1. First, apply the small shutdownCtx fix in cmd/server/main.go.
  2. In internal/queue/task.go or a new file:
    • Create a MultiProcessor struct that holds a slice of processors: 
      type MultiProcessor struct {
    processors []Processor
}

func NewMultiProcessor(processors ...Processor) *MultiProcessor {
    return &MultiProcessor{processors: processors}
}
    • Implement Process(ctx context.Context, payload string) error: Loop through all processors and run them. If any processor returns an error, stop and return that error!
  3. Test it with multiple processors in queue_test.go (e.g. an InventoryProcessor and an EmailProcessor)!
