1. The Problem: What Happens Under Unbounded Load?

Imagine your order service experiences a sudden spike: 10,000 requests hit POST /orders in 2 seconds.

Without backpressure:

  1. 10,000 HTTP goroutines spawn, exhausting RAM.
  2. SQLite database connections saturate, throwing database is locked.
  3. Response times degrade from 10ms to 30 seconds.
  4. Your health checks (/readyz) time out, causing Kubernetes / orchestrators to kill and restart your server.

The Senior Law of Backpressure: It is far better to reject excess traffic immediately with HTTP 429 Too Many Requests than to let your entire infrastructure crash.

2. The Token Bucket Algorithm

The Go standard extended library provides golang.org/x/time/rate:

  • Capacity (Burst): The maximum number of requests allowed in a sudden burst (e.g. 5 requests).
  • Fill Rate: How many tokens are added back to the bucket each second (e.g. 2 tokens/sec).
import "golang.org/x/time/rate"

// Fill rate: 2 tokens/sec, Bucket size: 5 tokens
limiter := rate.NewLimiter(rate.Limit(2), 5)

if !limiter.Allow() {
    // 429 Too Many Requests!
}

3. The Memory Leak Trap in Per-IP Rate Limiting

In production, you want to limit each IP address separately. A common junior mistake:

var limiters = make(map[string]*rate.Limiter) // ⚠️ DANGER: Infinite memory leak!

Over a few days, 500,000 unique IP addresses visit your site. The map grows forever and eventually triggers an Out-Of-Memory (OOM) crash!

The Senior Fix: Store a lastSeen time.Time for each client, and run a background ticker to periodically prune clients that haven't been seen in the last 5 minutes.
