Lesson 0027: Data vs. Code: The Persistence Boundary & Pure Generic Queues

Target: Master the fundamental architectural boundary between Data (State) and Behavior (Code), and build a clean, pure Generic Queue in Go.

First: You Are Not "Bad" At All!

You hit the exact same mental wall that led to the creation of Celery, Temporal, and RPC systems! You asked yourself: "A task has data and an action... but how do I save an action to SQLite?"

The answer is: You can't. And you shouldn't! Let's understand why.

1. The Golden Law: Databases Store State, Not Code

Layer What It Holds Examples Can It Be Saved to SQL?
State (Data) Values, numbers, strings, JSON, timestamps order.ID, order.Amount, "PENDING" ✅ YES (SQLite columns)
Behavior (Code) Functions, interfaces, closures, goroutines processor.Process(...), func() error ❌ NO (Cannot serialize a memory pointer)

When you defined:

type Task[T any] struct {
    Item      T
    Processor Processor[T] // ⚠️ Memory pointer to Go code!
}

And tried to call taskStore.Save(ctx, task), SQLite looked at task.Processor and said: "What on earth is a Go function address? I only know TEXT, INTEGER, and BLOB!"

Even worse: when your server crashes and restarts, how could SQLite recreate that function pointer? It can't!

2. How Real Senior Systems Separate the Two

There are two clean ways production systems handle this:

Approach A: Pure Generic Concurrency Queue (What Lesson 0026 Asked For)

Keep the Queue as a pure in-memory concurrency tool. It coordinates goroutines, buffers, and shutdown in RAM, and leaves database persistence to domain stores!

// In internal/lib/queue.go:
type Queue[T any] struct {
    processor func(context.Context, T) error // The Queue owns the action in RAM!
    items     chan T
    // ...
}
  • The HTTP handler only touches Data: saves Order to SQLite.
  • The Outbox Dispatcher reads *Order from SQLite, and passes it to orderQueue.Submit(ctx, order).
  • The Queue workers run the processor on the order!

Approach B: The Task Name Registry (How Celery / Asynq / Temporal work)

If you really want a universal tasks table in SQLite for different types of jobs (Orders, Emails, Invoices), you do not save the Go code. You save a String Name!

// In Database:
// id: "task_123", type: "order.fulfill", payload: {"order_id": "456"}

// In Go: Register your handlers at boot:
registry := map[string]Processor{
    "order.fulfill": orderProcessor,
    "email.send":    emailProcessor,
}

// In Worker: Look up the code by its string name!
handler := registry[task.Type]
handler.Process(ctx, task.Payload)
