1. The Real-World Dilemma: Transient vs. Fatal Failures

In our current pipeline, if PaymentProcessor or another external service encounters a 500ms network timeout or 503 Service Unavailable:

  1. The processor returns an error.
  2. The worker immediately triggers cleanup() (releasing reserved stock!).
  3. The order is marked StatusFailed and discarded forever.

In high-volume e-commerce (and distributed systems in general), network hiccups happen all the time. Canceling a customer's order on the very first transient glitch loses revenue and creates angry customers.

Instead, production systems categorize errors:

  • Fatal (Non-Retryable) Errors: e.g., ErrInsufficientStock, Invalid Item ID, Stolen Card. → Fail immediately, execute rollback.
  • Transient (Retryable) Errors: e.g., HTTP 500, network timeout, rate limit exceeded. → Retry with backoff!

2. Exponential Backoff & Jitter

If an external payment gateway is overloaded, hammering it again immediately will only make the outage worse (the "thundering herd" problem).

Instead, we back off exponentially between attempts:

Attempt 1: wait 100ms
Attempt 2: wait 200ms
Attempt 3: wait 400ms
...

In Go, this calculation is simple and clean:

backoff := baseDelay * time.Duration(1 << order.Retries) // 2^retries
select {
case <-ctx.Done():
    return ctx.Err()
case <-time.After(backoff):
}

3. The Dead-Letter Queue (DLQ)

What happens if an order fails 3 times in a row and retries are exhausted?

We do not delete it or leave it in a mystery state. We transition it to a dedicated state:

const StatusDeadLetter OrderStatus = "DEAD_LETTER"

A Dead-Letter status signals to operations and customer support: "This order failed repeatedly after maximum retries. It requires manual review or automated alerting."

4. Error Classification in Idiomatic Go

How do we tell if an error is retryable without tight coupling? Go Interfaces!

// Transient errors implement this interface:
type Retryable interface {
    Retryable() bool
}

func IsRetryable(err error) bool {
    var r Retryable
    if errors.As(err, &r) {
        return r.Retryable()
    }
    return false
}

Or with sentinel errors using errors.Is(err, ErrTransient)!
