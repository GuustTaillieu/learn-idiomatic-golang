Lesson 0004: Testing Concurrency and the Race Detector

Target: Write robust tests for concurrent Go code and verify safety with go test -race.

Win: You completed the core Queue lifecycle: New, Submit, Start, and Stop! Now we verify it like senior engineers: using native tests, mock-free stubs, and the Go race detector.

1. The Go Race Detector (go test -race)

Concurrent bugs (data races) are notoriously hard to reproduce because they depend on thread interleaving and CPU scheduling. They might work 99.9% of the time and crash in production under load.

Go has a superpower built into the toolchain: ThreadSanitizer. When you add the -race flag:

go test -v -race ./internal/queue

The compiler instruments every memory access. If two goroutines access the same variable at the same time and at least one is a write, Go immediately fails the test and prints a detailed stack trace of both goroutines!

2. Mock-Free Interface Stubs

In senior Go, we rarely reach for heavy third-party mocking frameworks for small interfaces. Because our Queue accepts the Processor interface:

type Processor interface {
    Process(ctx context.Context, payload string) error
}

We can create a lightweight test stub right inside our _test.go file:

type mockProcessor struct {
    mu        sync.Mutex
    processed []string
}

func (m *mockProcessor) Process(ctx context.Context, payload string) error {
    m.mu.Lock()
    defer m.mu.Unlock()
    m.processed = append(m.processed, payload)
    return nil
}

Notice that because multiple workers call Process() concurrently, our test stub also protects its slice with a mutex! That's concurrency discipline end-to-end.

3. The Golden Rule of Concurrent Tests: Never Rely on time.Sleep

Novice tests often do this:

q.Submit(...)
time.Sleep(100 * time.Millisecond) // ❌ FLAKY!
assert(...)

Why is this an anti-pattern? On a busy CI runner, 100ms might not be enough and the test fails randomly. Or it wastes seconds sitting idle.

Instead, we rely on synchronization: calling q.Stop() blocks until all workers drain and finish. Once Stop() returns, we are 100% guaranteed that all submitted tasks have completed!

Your Hands-On Challenge: Write internal/queue/queue_test.go

Create internal/queue/queue_test.go:

  1. Declare package queue and import testing, context, sync, and errors.
  2. Create your mockProcessor struct with a mutex and a slice of received payloads.
  3. Write TestQueue_SubmitAndProcess(t *testing.T):
    • Create a mock processor, context, and a new queue.
    • Start 3 workers: q.Start(ctx, 3).
    • Submit 5 tasks in a loop.
    • Call q.Stop().
    • Check that the number of processed tasks is exactly 5!
  4. Write TestQueue_SubmitAfterStop(t *testing.T):
    • Create a queue and call q.Stop() immediately.
    • Try calling q.Submit(...) and verify it returns ErrQueueClosed using errors.Is(err, ErrQueueClosed).
  5. Run your tests in your terminal with: 
    go test -v -race ./internal/queue
